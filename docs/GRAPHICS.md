# Graphics: sheets, tiles and sprites

Contract for art in games. Owner decisions (2026-11-13):

- Art comes in as **sheets** (one image holding a grid of cells) and as
  single images, which are simply sheets with one cell.
- Terrain can **join** with its neighbours using a 16-piece set (roads,
  rivers, walls). Full 47-piece blending is not in this step.
- Units of different sides are told apart by a **colour marker** the engine
  draws; a game may also give a side its own art.
- The engine ships a plain **original starter art set** (generated by a
  script in this repo, no third-party art).
- Simple looping animation is included. Walking/attack animation is later.

Everything is optional: a game without `data/graphics.json` looks exactly
as before (coloured squares and letters), and any terrain, structure or unit
without art keeps that placeholder look next to ones that have art.
Structures (buildings standing on terrain, docs/STRUCTURES.md) have art like
units do, drawn across their whole footprint.

## File format: data/graphics.json

```jsonc
{
  "sheets": [
    { "id": "tiles", "file": "art/tiles.png", "cellWidth": 24, "cellHeight": 24 },   // "smooth": true for detailed art
    { "id": "knight", "file": "art/knight.png", "cellWidth": 24, "cellHeight": 24 }  // a single image
  ],
  "unitMarker": true,                      // optional, default true (see "Units")

  "terrain": {                             // terrain id -> look
    "plain":  { "sheet": "tiles", "variants": [[0,0],[1,0],[2,0]] },
    "forest": { "sheet": "tiles", "cell": [3,0] },
    "sea":    { "sheet": "tiles", "frames": [[0,1],[1,1]], "frameMs": 500 },
    "road":   { "sheet": "tiles", "join": [0,2], "joinWith": ["bridge"], "joinEdge": true }
  },
  "structures": {                          // structure id -> look (like a unit's)
    "city": { "sheet": "buildings", "cell": [0,0] },
    "castle": { "sheet": "castle", "cell": [0,0],           // 2 x 2 squares: a cell 48 wide, taller
                "sides": { "red": { "sheet": "castle", "cell": [1,0] } } }
  },
  "portraits": {                           // dialogue portraits (see "Portraits")
    "eirik": { "sheet": "faces", "cell": [0,0] }
  },
  "units": {                               // unit type id -> look
    "knight": { "sheet": "knight", "cell": [0,0] },
    "soldier": { "sheet": "men", "frames": [[0,0],[1,0]], "frameMs": 450,
                 "sides": { "red": { "sheet": "men", "cell": [0,3] } } }
  },

  "styles": {                              // visual style id -> overrides
    "night": { "terrain": { "plain": { "sheet": "tiles", "cell": [0,6] }, "sea": null },
               "structures": { "city": { "sheet": "buildings_night", "cell": [0,0] } },
               "units": { } }
  }
}
```

- A sheet may also have `"name"`: a display name for editors; the engine
  ignores it (like any key it does not know).
- A sheet may have `"smooth": true` (default `false`, the hard pixels of
  pixel art): for detailed, high-resolution art. **In the 3D kinds of view**
  the sheet is sampled with blending between pixels and with mipmaps
  (shrunk-down copies, so far-away detail does not shimmer; the software 3D
  drawer blends pixels only). Hard-pixel sheets look exactly as before. The
  2D views (top-down and 2D isometric) do not use the key yet: not yet.
  Must be `true` or `false`. A smooth sheet's pictures are cut half a pixel
  inside their cell so neighbouring cells do not bleed in; leave a little
  margin round detailed pictures that touch their cell's edge, and note that
  see-through edges of smooth art may show a faint dark rim in the shrunk
  copies (the colour under fully transparent pixels takes part).
- 3D textures are padded to power-of-two sides (a 1500 x 1000 sheet is a
  2048 x 1024 texture). The largest texture is what the 3D drawer takes:
  the graphics driver's limit but at most 4096 on OpenGL, 2048 in software.
  A sheet is at most 2048 x 2048 anyway (the loader refuses more), so it
  always fits; if a drawer ever had less, the sheet is refused with a plain
  message in the log and what uses it keeps the placeholder look, never a
  crash.
- Sheet images are PNG files inside the game folder (by convention in
  `art/`), at most 2048 x 2048 pixels. Cells are counted `[column, row]`
  from 0 at the top-left. Pixels right of / below the last whole cell are
  ignored. No margins or gaps between cells in this version.
- A look has `sheet` and exactly one of:
  - `cell`: one cell.
  - `variants` (terrain only): alternates. Each map square always shows the
    same one (chosen from its position), so fields do not look like
    wallpaper and do not flicker.
  - `frames`: cells played in a loop, `frameMs` each (default 400).
  - `join` (terrain only): top-left cell of a 4 x 4 block of 16 pieces (8 x 8 block of 64 on a
    hexagon game, see docs/HEX.md "Join pieces on hexagons"), see below. It may also be a list of such cells, `[[0,2],[4,2]]`: the blocks
    are then played as an animation (`frameMs` each, up to 16), so water or
    lava can shimmer AND join. `joinWith` lists other terrain ids that count as "the same" when
    choosing a piece; or use `joinExcept` instead to join with EVERY terrain
    except the listed ones (a bridge joins all land, so its ends reach the
    bank, but not the water it crosses); `joinEdge` (default true) makes the map edge count too.
- `units.<id>.sides.<side id>` gives a side its own look (side ids are the
  `id`s in a map's `sides`).
- `structures.<id>` is exactly like a unit entry (`cell` or `frames`, optional
  `sides`; `variants` and `join` are not allowed). With `sides`, the look of the
  structure's current owner is used (neutral structures use the base look).
- `styles.<style id>` overrides entries for one visual style of `game.json`.
  A style whose kind of view is not top-down inherits nothing and needs its
  own pictures, drawn by other rules: docs/VIEWS.md "Art".
  `null` removes the art for that style (placeholder look). Entries not
  mentioned are inherited.

Loader: `engine/core/data/loader_graphics.cpp` (errors read
`data/graphics.json: terrain "plain": …`, `structure "city": …`). In memory:
`Database::graphics` (`engine/core/data/graphics.h`), with one already-merged
`GraphicsSet` per style (`terrain` per terrain index, `units` per unit type,
`structures` per structure type, the last two as `UnitLook`) and `pickCell()`
to choose the cell for a square.

### The 16 join pieces

(Hexagon games use six neighbours and an 8 x 8 block of 64 pieces: docs/HEX.md "Join pieces on hexagons".)

A piece is chosen by which of the four neighbours count as the same
terrain: **N = 1, E = 2, S = 4, W = 8**, added up to a number 0..15. Piece
`n` sits at column `n % 4`, row `n / 4` of the block:

```
        col 0      col 1      col 2      col 3
row 0   0 alone    1 N        2 E        3 N+E
row 1   4 S        5 N+S      6 E+S      7 N+E+S
row 2   8 W        9 N+W      10 E+W     11 N+E+W
row 3   12 S+W     13 N+S+W   14 E+S+W   15 all four
```

So a road running left-right is piece 10, a dead end pointing up from a
square is piece 4 (its only neighbour is to the south), a crossroads is 15.

## Portraits (dialogue)

```jsonc
"portraits": { "eirik": { "sheet": "faces", "cell": [0,0] },
               "gorm_angry": { "sheet": "faces", "cell": [1,0] } },
"styles": { "night": { "portraits": { "eirik": { "sheet": "faces", "cell": [0,1] }, "gorm_angry": null } } }
```

The picture beside a line of dialogue (docs/EVENTS.md "Dialogue (player)").
Each entry is exactly one `cell` of a sheet. The id is what a line of
dialogue asks for: the line's own `portrait`, else the speaking unit's story
id. An id that has no entry just shows the dialogue box without a picture.
A style's `portraits` replace the general ones per id and `null` removes
one, like the other per-style art. Unlike terrain and units, **every style
starts with the general portraits, whatever its kind of view**: a face is
not drawn differently for the isometric or 3D kinds (a style can still
replace or remove one). Errors read `data/graphics.json: portrait "eirik": …`
(unknown sheet, a cell outside the sheet, `frames` instead of one cell).

The box draws a portrait 48 x 48 logical pixels with the 8 px font (more
with larger fonts / UI scale), keeping the cell's proportions (fitted
inside, standing on the box's bottom edge), so square cells or cells a bit
taller than wide work best. The 2D renderer draws every sheet the same way,
so the sheet's `smooth` key has no effect on portraits yet.

In memory: `GraphicsSet::portraits` and `GraphicsSet::portrait(id)`;
player: `BattleScene::portraitFor` (battle_story.cpp).

## Models (3D kinds of view only)

In a style whose kind of view is 3D (`isometric-3d`, later `3d`; see
docs/VIEWS.md) a unit or a structure can be a 3D model instead of a
picture. The maker chooses per thing; pictures and models mix freely in one
style.

```jsonc
"styles": {
  "solid": {                                  // a style with "view": "isometric-3d"
    "units": {
      "knight": { "model": "models/knight.glb" },
      "archer": { "model": "models/archer.glb",
                  "height": 1.2,              // how tall it stands, in squares (default 1.0)
                  "turn": 180,                // degrees added to its facing (a model that does not face +Z)
                  "sideMaterial": "cloth",    // the material that takes the side's colour (default "side"; "" = none)
                  "animations": { "idle": "Breathe", "move": "Run", "attack": "Shoot", "die": "Fall" } }
    },
    "structures": { "fort": { "model": "models/fort.glb" } }
  }
}
```

- `model`: a glTF file (`.glb`, or `.gltf` with its files) inside the game
  folder, by convention in `models/`. What the engine reads from it:
  docs/RENDER3D.md "Models". An entry with `model` cannot have `sheet`,
  `cell`, `frames`, `frameMs` or `sides`.
- The model stands with its origin on the ground in the middle of the
  square, +Y up, facing +Z. It is scaled as a whole so that its rest pose is
  `height` squares tall (measured from its origin). A structure without
  `height` is scaled so that its wider side fills 0.92 of the shorter side
  of its footprint.
- Textures of the model follow the glTF sampler: `magFilter` NEAREST (9728)
  = hard pixels; anything else, or no sampler, = smooth with mipmaps. The
  models this repository makes (`tools/art/make_test_model.py`) say NEAREST
  and look as before; the unit and bend models have no textures.
- Side colour: every material named `sideMaterial` is multiplied by the
  colour of the unit's side (a structure: its owner's; nobody's: a pale
  grey). Make that material white or light in the file. The `unitMarker`
  square under a unit's feet is drawn as well.
- Animations are named clips in the file. The view plays, by default,
  `Idle` (looped; also for structures), `Move` (looped, while the unit
  travels), `Attack` (once, when it strikes) and `Die` (once, spread over
  the time the unit takes to vanish). `animations` gives other names. A
  name the file does not have means the rest pose for that state.
- A unit faces the way it moves and strikes; when first seen it faces the
  nearest enemy. A unit that has acted is drawn darker.
- A terrain can have a standing part too: "Standing terrain" below.
- Errors: outside a 3D style (`a "model" can only be used in a style whose
  kind of view is 3D`), a missing file, a wrong extension and unknown
  animation states are refused when the game loads. A file that exists but
  cannot be read as a model is reported in the log when the battle starts
  and the thing keeps its placeholder look.

In memory: `UnitLook::model` (`ModelLook`). Player:
`engine/player/battle/models3d.*` (loading, posing, drawing) and
`map3d_models.cpp` (which animation, facing).

## Standing terrain (3D kinds of view only)

In the two 3D kinds of view a terrain's picture is laid flat on the top of its block. A terrain can also have
a **standing part** on that ground: an upright picture that faces the camera, or 3D models. The maker chooses
per terrain, the way units choose between a picture and a model; the ground picture (the terrain's own `sheet`
and `cell` / `variants` / `frames` / `join`) stays underneath and keeps joining, the standing part is per square.

```jsonc
"styles": {
  "solid": {                                  // a style with "view": "isometric-3d" or "3d"
    "terrain": {
      "forest": { "sheet": "ground", "cell": [0, 0],          // the flat ground picture, as always
                  "stand": { "sheet": "trees", "variants": [[0,0],[1,0],[2,0]],   // an upright picture, a random mix
                             "width": 30, "scatter": true } },
      "mountain": { "sheet": "ground", "cell": [1, 0],
                    "stand": { "variants": ["models/peak_a.glb", "models/peak_b.glb"],   // models, one per square by position
                               "height": 1.3, "turn": 20, "scatter": true } },
      "wall": { "sheet": "ground", "cell": [2, 0],
                "stand": { "model": "models/wall.glb" } }
    }
  }
}
```

- **A picture** needs `sheet` and exactly one of `cell`, `variants` (1 to 64 pieces; each square always shows the
  same one, chosen from its position by the same hash terrain variants use, so a forest is not a row of identical
  trees and nothing flickers) or `frames` (played in a loop, `frameMs` each, default 400). `width` (whole number,
  1 to 512) is how wide it is drawn in the game's tile pixels (`tileSize` = one square); empty = one square. Height
  keeps the piece's proportions. Pieces are cut out: transparent pixels show what is behind.
- **Models** need either `model` (one `.glb` / `.gltf` file) or `variants` (a list of 1 to 64 such files, each
  square picks one by its position), never both. `height` (0.1 to 16 squares, default 1) is how tall they stand
  and `turn` (-360 to 360 degrees) is added to the way they face; both apply to every file of the entry. The same
  rules as unit models otherwise (docs/GRAPHICS.md "Models": origin on the ground in the middle, +Y up, lit by
  the map's sun; a file that exists but cannot be read is logged when the battle starts and that terrain keeps its
  ground picture only). Terrain has no side colour and no animations: models stand in their rest pose.
- `scatter` (true / false, default false) gives every square a small fixed shift (and each model its own turn),
  worked out from the square's position, so it is the same every frame, on every platform and after a save.
- The terrain still needs a ground picture of its own (`sheet` etc.): the standing part stands on it. A style that
  gives a terrain `null` (no art) has no standing part either, and so does a terrain with no entry.
- **Only in a style of a 3D kind** (`isometric-3d`, `3d`). A `stand` anywhere else (the general art, a top-down
  or 2D isometric style) is refused when the game loads: `data/graphics.json: style "day": terrain "forest" stand:
  a "stand" can only be used in a style whose kind of view is 3D ("isometric-3d" or "3d"); other styles draw a terrain
  as its picture only`. Those two 2D kinds draw exactly as before, whether or not another style of the game has one.
- **Strict**: a `stand` has only the keys above (and `null` = none). Refusals read `data/graphics.json: <where> stand:
  <message>`: `needs a "sheet" (an upright picture) or a "model" (a 3D model)`; `has an unknown key "colour"`;
  `is a picture, so it cannot have "turn"` / `has a "model", so it cannot also have "sheet"` (picture keys are
  `sheet cell frames variants frameMs width`, model keys `model variants height turn`); `needs exactly one of "cell",
  "variants" or "frames"`; `needs exactly one of "model" (one file) or "variants" (a list of model files)`;
  `unknown sheet "x"`; `cell [9, 9] is outside sheet "trees" (4 x 2 cells)`; `"width" must be between 1 and 512 ...`;
  `"height" must be between 0.1 and 16 (squares)`; `"turn" must be between -360 and 360 (degrees)`; `"variants" must list
  between 1 and 64 model files` / `"variants" must list model files (text)`; `model file "models/x.glb" does not exist`; `a
  model must be a .glb or .gltf file inside the game folder ...`. Games without a `stand` load, draw and save exactly as before
  (art is never hashed or saved: rules never see it).
- **Where it stands** and what happens to units, the cursor, ranges and fog: docs/VIEWS.md "Standing terrain".

In memory: `GraphicsSet::stands` (per terrain index, `StandLook`: `picture` (a `Look`), `width`, `models`
(`ModelLook`, one per variant), `scatter`), chosen with `pickStandCell`, `pickStandModel` and `standScatter`
(`engine/core/data/graphics.*`, tests in `tests/test_graphics_stand.cpp`). Player: `engine/player/battle/map3d_stand.cpp`.

## Drawing rules (player and editor canvas must match)

Terrain with art:
- The cell is stretched to the map square (nearest-neighbour, no smoothing).
- The placeholder fill, the faint square outline and the letter are not
  drawn. Owner frames, highlights, cursor and capture numbers are unchanged.
- Transparent pixels show the placeholder colour of that terrain underneath
  (so art with holes still looks right): fill first, then the cell.

Units with art:
- Width = one map square. Height keeps the cell's proportions; the sprite
  sits on the bottom edge of the square, centred, and may stick out above
  it (tall sprites). Units are drawn top row first so lower units overlap
  higher ones.
- Marker (when `unitMarker` is true): a flat base in the side's colour
  under the sprite's feet: a filled bar across the bottom of the square,
  about a sixth of the square high, inset one pixel, with a 1-pixel dark
  outline. Drawn before the sprite. The HP bar stays where it is today, on
  top of the base.
- A unit that has already acted is drawn darker (colour multiply about
  55 %) instead of the grey mix used for placeholder blocks.
- Leader pip, pop-in/scale, fade (alpha) and hit shake work as before.
- Animation phase uses the battle's running time; all units of a type are
  in step.

Unit with no art: today's coloured block with a letter, unchanged.

Structures (docs/STRUCTURES.md "Drawing"; the editor canvas matches):
- Order: all terrain first; then structures and units together, sorted by the
  pixel row of their bottom edge, structures before units in the same row. A
  unit standing on a structure square always sorts with that structure's bottom
  edge, so it is drawn over the structure it stands on (also on the upper rows of
  a multi-square footprint); a tall structure covers what stands behind it.
- With a picture: the sheet cell is drawn across the whole footprint: width =
  `width` squares, height keeps the cell's proportions (nearest-neighbour), and the
  bottom edge sits on the footprint's bottom edge, so a taller picture sticks out
  above it (towers, chimneys, flags). Transparent pixels show the terrain below.
  Animated looks play with the battle's running time.
- Without a picture: a block in the structure's colour over the footprint, inset one
  pixel, with a 1-pixel dark outline, a soft top highlight and the letter centred
  (`styles.<id>.structureColors` recolors it; `showGlyphs: false` hides the letter).
- Owner: a 2-pixel frame in the owner's colour around the whole footprint
  (drawn with the structure, so units drawn later stand over it).
- Move/attack highlights are painted again over the structure's squares after it is
  drawn (otherwise its picture would hide the terrain pass's tint).
- Capture points remaining are shown once per structure, on the capturing unit's square.

## Platform: textures

`engine/platform/platform.h` gains (all backends must implement):

```cpp
typedef int TextureId;   // 0 = none

class Renderer {
  // Creates a texture from 32-bit pixels (R,G,B,A bytes, row by row, not
  // premultiplied). Nearest-neighbour scaling, or linear with `smooth` (used
  // for the 3D picture only). 0 on failure (logged).
  virtual TextureId createTexture(const uint8_t* rgba, int width, int height, bool smooth = false) = 0;
  virtual void destroyTexture(TextureId id) = 0;
  // Draws part of a texture (sx,sy,sw,sh in texture pixels) into a rectangle
  // in logical pixels. `mod` multiplies colour and alpha (white = as is).
  virtual void drawTexture(TextureId id, int sx, int sy, int sw, int sh,
                           int dx, int dy, int dw, int dh, Color mod = Color(255, 255, 255)) = 0;
};
```

PNG decoding lives in `engine/platform/common/image.{h,cpp}` using
`third_party/stb/stb_image.h` (PNG only: `STBI_ONLY_PNG`, no stdio use
beyond what the repo's file helpers do, no exceptions). The core never
decodes images. Textures must survive `setLogicalSize`. Headless runs and
`--screenshot` must show the art.

A sheet that fails to decode logs one clear error and everything using it
falls back to the placeholder look; the game still runs.

## Starter art

`tools/art/make_starter_art.py` (Python + Pillow, deterministic, no input
files) draws the starter set and writes the PNGs and `data/graphics.json`
into both demos and the three editor templates. Art is original to this
project: simple flat pixel art, 24 x 24 cells (the games' `tileSize`), with
a limited palette. It must cover every terrain, structure and unit type those games
define, and must exercise every feature: variants (plain), join
(roads), animated join (water/sea and bridges), a two-frame unit idle, and at least one
per-style override in a demo that has styles. Re-running the script
reproduces identical files.

In the pixel-art 3D styles of both demos (`isometric-3d`, `full-3d`) the forest and the mountain have plain ground
pictures (a leafy floor and bare rock, sheet `ground3d`, 24 x 24 cells) with an upright picture standing on them
(sheet `stand`, 24 x 32 cells: three clumps of trees as a random mix, two sets of peaks), drawn by
`tools/art/art_stand.py` into `art/stand.png` and `art/ground3d.png` and written into `data/graphics.json` by
`make_starter_art.py`. The templates have no 3D styles and no standing parts.

`demo-srpg` also has a "Detailed 3D" style for trying the 3D views with
detailed art: smooth 512-pixel ground pictures and animated character
models from public-domain packs (`games/demo-srpg/CREDITS.md`); its forest and mountain squares have
standing models (`models/detailed/forest_{a,b,c}.glb`, `mountain_{a,b}.glb`, generated low-poly trees and
peaks written by `tools/art/make_terrain_models.py`, no downloads) on the flat ground textures. It is built
by `tools/art/make_detailed_style.py` (which uses `tools/art/trim_glb.py`
to cut a model file down to chosen parts and animations) into
`art/detailed.style.json`; `make_starter_art.py` merges every
`art/*.style.json` of a game into its `data/graphics.json`.

**Unit pictures and models of the story demo.** Every unit type of `demo-srpg` has art of its own in every style (the
seven promoted and summoned types, Captain, Lancer, Outrider, Marksman, Brute, Houndmaster and Hound, are no longer drawn
as the type they grow from; the template's Outrider has its own row too):

| Style | Where a unit's picture comes from | Made by |
|---|---|---|
| Classic, Parchment | sheet `units` (24 x 24, two idle frames per row; Parchment has no unit art of its own) | `art_units.py` (the older types) and `art_units_promoted.py` (the seven) |
| Isometric | sheet `iso_units` (the same sprites cut under the feet) | `art_iso.py` from the same drawing functions |
| 3D isometric, Full 3D | `models/<unit>.glb`, generated low-poly block figures with Idle / Move / Attack / Die | `make_unit_models.py`, the seven in `unit_models_promoted.py`; `height` in `graphics.json` makes the bigger (Brute, Lancer) and the smaller (Hound) kinds stand at their size, because the engine fits a model's whole rest pose to one height |
| Detailed 3D | `models/detailed/<unit>.glb`, CC0 character packs cut down and dressed | `make_detailed_style.py` (the older seven: `make_detailed_units.py`; the new seven: `make_detailed_promoted.py`, with `glb_gear.py` for parts of other models, generated blocks and tints) |

The Hound is a four-legged dog in every style (its own skeleton: spine, head, tail, four legs; in Detailed 3D the CC0
"Husky" model). A promoted type is drawn as a grander or lighter version of its source: the Captain has a plumed helm,
gold and a long cape; the Lancer is plated on an armoured horse with a long pennant lance; the Outrider a hooded light
rider with a sword; the Marksman an archer with a tall bow and a full quiver; the Brute a horned fighter with a great
axe; the Houndmaster wears a fur collar and cap and has a whistle, a sword and a leash. In the 3D styles the promotion
screen still shows a unit type's letter on a side-coloured block (a look is either a picture or a model, and the screen
draws pictures only); in Classic, Parchment and Isometric it shows the new sprite. `tests/srpg_art_test.py` checks that no
two unit types of a style share a look.

Models can also be **combined** by the art tools (`tools/art/glb_merge.py`, `glb_attach.py`, `glb_pose.py`; recipes in
`make_detailed_units.py`, `make_detailed_promoted.py`): a rigid model (a weapon) is hung on a character's hand joint, and a rider's whole skeleton
is made a child of a mount's body joint, so one file holds two skeletons and one clip (`Idle`, `Move`, `Attack`, `Die`)
animates both. The loader needs nothing new for this (several skins, rigid meshes under joints and clips over any node
are standard glTF it already reads). Two things to know when making such models: the engine scales a unit by its
rest-pose bounds measured from the raw vertices, so a combined model must have its rest pose (and the bind pose of its
skins) be what it should look like (`Glb.rebind_rest()`); and a rigid weapon turns with the wrist, so
`steer_weapon()` keys the weapon's own pivot to keep it pointing the way the picture needs in every clip.
`glb_gear.py` adds three more: `load_part()` / `attach_part()` take one rigid part (a sword, a shield, a helmet) out of
a pack and hang it on another model's joint where the pack had it (the KayKit characters share one skeleton),
`add_blocks()` adds generated boxes (a plume, a collar, horse barding) that follow a joint, and `tint()` multiplies a
material's colour.

## Editor helper API additions (docs/EDITOR_API.md is updated to match)

- `GET /api/projects/:id` gains `"graphics"`: the contents of
  `data/graphics.json`, or `null` when the file does not exist (that is not
  a problem). A file that is not valid JSON: `null` plus a problem, as for
  the other sections.
- `PUT /api/projects/:id` accepts `"graphics"` (object: written to
  `data/graphics.json`; absent or `null`: left untouched).
- `GET /api/projects/:id/art` → `{ "art": [ { "file": "art/tiles.png",
  "width": 96, "height": 48, "size": 1234 } ] }`: every `.png` in the
  project's `art/` folder, sorted by name. Unreadable/non-PNG files are
  listed with `width`/`height` 0 and an `"error"` text.
- `PUT /api/projects/:id/art/<name>.png`: body is the raw PNG bytes. `name`
  matches `[a-z0-9][a-z0-9_-]{0,39}`. Checks: PNG header, at most
  2048 x 2048 pixels, at most 8 MB. `201 { "file", "width", "height",
  "size", "revision" }`. An existing file is only replaced with
  `?overwrite=1`, otherwise `409`. Written atomically; creates `art/`.
- `DELETE /api/projects/:id/art/<name>.png`: `409 { "error", "usedBy":
  ["sheet id", …] }` while a sheet in the saved `data/graphics.json` uses
  the file; otherwise deletes it → `200 { "revision" }`. `404` if missing.
- `GET /api/projects/:id/file/<path>` answers `image/png` for `.png` files.
- The project `revision` covers art files, so uploads/deletes change it and
  both calls return the new one.
- Creating a project from a template copies its `art/` folder byte for byte.
- Problems come from the real loader, with `file: "data/graphics.json"`.

## Editor UI

Specified in docs/EDITOR_UI.md ("Art", "Standing terrain"). In short: a new **Art** section to
import images and set how they are cut into cells; a **Picture** part on
each terrain and unit to choose cells with a click; and the map canvas
draws with the art using the rules above.

## Implementation notes

What the first implementation does, where it is, and where it differs from
the contract above.

- **Where things live.** `engine/platform/common/image.{h,cpp}` (PNG decode,
  `stb_image_impl.cpp` compiles stb_image with `STBI_ONLY_PNG`, `STBI_NO_STDIO`;
  version and checksum in `third_party/stb/README`); texture calls in
  `sdl3/sdl_renderer.cpp` and `sdl2/sdl2_renderer.cpp`; `engine/player/battle/sprites.{h,cpp}`
  (sheet textures, terrain and unit drawing); `joinMaskAt()` in
  `engine/core/data/graphics.{h,cpp}` (the pure neighbour test, unit-tested
  in `tests/test_art.cpp`); the generator in `tools/art/`.
- **Texture lifetime.** `PlayerApp` owns one `Sprites` object and decodes the
  game's sheets right after `GameSession::load`; `dropSession()` frees them
  before the session goes (home, game page, options, loading another game).
  `Sprites` never frees in its destructor, because at shutdown the renderer
  is already gone; each backend frees whatever textures are left when the
  renderer is destroyed.
- **Failure.** A sheet that cannot be decoded logs one line
  (`art sheet "units" (art/units.png): ...; what uses it keeps the placeholder look`)
  and only the things using that sheet fall back; terrain and units that
  use other sheets keep their art. (A file whose header is not a PNG is
  already rejected by the loader as a game error, as before.)
- **Units.** The sprite is drawn after the marker. The marker's colour is
  the 4 pixel rows of fill inside its 1 px outline (`t / 6` high, at least 2).
  Because the HP bar sits on the same rows, an art unit's HP bar is drawn as a
  dark 2 px track with the fill on it and **no black outline** (deviation from
  "stays where it is today": same position and size, but the outline is
  dropped so the base's colour stays visible above, below and beside the bar;
  with the outline the sides could not be told apart). With
  `unitMarker: false` the bar keeps its outline. Pop-in scales the sprite
  around its own centre and shrinks the base's width with it. A unit that
  has acted gets colour multiply 0.55 on both the sprite and the base.
- **Structures in the player.** `Sprites` needs nothing new (structure sheets
  are ordinary sheets). `structureArt()` / `drawStructureArt()` in
  `engine/player/battle/sprites.cpp`; the per-structure pass (picture or
  placeholder block, owner frame, highlight re-tint) is `drawStructure()` in
  `engine/player/battle/structure_draw.cpp`, called by `drawMap()` in sorted order. The info
  panel shows the structure under the cursor with its own small swatch (its picture
  squeezed into it) after the terrain line, then the merged numbers.
- **Info panel.** The small terrain swatch of the panel draws the terrain's
  art (stretched into the swatch, and for joined terrain with the piece of
  the inspected square). Unit and side chips in the panel and the forecast
  box are flat colours today and stay that way.
- **Starter art.** `python3 tools/art/make_starter_art.py` (Pillow) writes
  `art/tiles.png` (8 x 18 cells), `art/units.png` (2 frames per unit, one row
  per unit type of that game) and `data/graphics.json` for the two demos and
  the three templates, plus `art/tiles_night.png` / `art/tiles_parchment.png`
  (tinted copies of the tiles, referenced by those styles) for the demos that
  have such styles. Roads (joined, also with bridges) use the 16-piece layout. Water (river and sea) is an
  **animated join**: two 4 x 4 blocks (frames), each piece drawing a sand bank with a foam
  line on the sides whose neighbour is not water, and open water on the others; it joins
  with the map edge and with bridges. A bridge joins everything except water (`joinExcept`),
  so its deck runs to the bank, and is an animated join over the same water. Unit sprites
  stand on row 17 of the 24 px cell so the engine's base and HP bar fill the
  bottom rows.
- **Structure starter art.** `tools/art/art_structures.py` draws the pictures
  (city with a clock tower, factory with tall chimneys, fort, a 1-square and a 2 x 2
  headquarters with a gold-roofed tower and flag). Each picture sits on a small paved
  plot and is outlined; its top rows stick out above the footprint (4 px for a 24 x 28
  cell, 8 px for the 48 x 56 cell of the 2 x 2 headquarters). One sheet per footprint
  size: `art/structures.png` (1 x 1, cells 24 x 28) and `art/structures_2x2.png`
  (cells 48 x 56); styles with a tint get tinted copies (`structures_night.png`...)
  and `styles.<id>.structures`. The tile sheet no longer has building tiles. Roads
  are not joined into buildings any more (buildings are not terrain); maps put
  road terrain under the structures a road leads into instead.
- **Hexagon starter art.** `python3 tools/art/make_hex_art.py` (Pillow) draws the same retro set on hexagons
  for `games/demo-hex` and the two hexagon templates (docs/HEX.md "Implementation notes (starter content)"): a
  tile sheet of hexagon cells (24 x 28 pointy, 28 x 24 flat) with transparent corners, roads as an 8 x 8 join block,
  water and the bridge as animated joins of two 8 x 8 blocks, one-hexagon structures (box width by box height + 4)
  and the fortress (`"rings": 1`) as one picture across its seven hexagons. Units are the square set's sprites.
  Original art, generated, GPL-3.0 like the rest of `tools/art/`; no third-party material.
- **Web.** Nothing special was needed: the pages already fetch and write
  every file as bytes, and `make_manifest.py` lists the PNGs. `tools/webtest`
  (standalone and embed suites) now fails when terrain art is not drawn.
